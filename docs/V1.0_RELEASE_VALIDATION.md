# ALTRun Next 1.0.0 Release Validation

ALTRun Next 1.0.0 is promoted directly from the validated v0.8.0-beta.3 hardening line. The release intentionally skips a separate RC cycle. The accepted product behavior becomes the first stable 1.x baseline; later non-blocking defects are handled through 1.0.x maintenance releases.

## Frozen release contract

- Version: `1.0.0`
- Windows fixed FileVersion/ProductVersion: `1.0.0.30000`
- Settings schema: 11
- Commands schema: 2
- Usage schema: 2
- Provider Cache schema: 22
- Architectures: x64 and ARM64
- Main launcher surfaces: Classic ALTRun and Modern Compact
- Stable release channel: GitHub `latest` versioned release
- Versioned tag and release assets are immutable.

## Automated publication gates

The `v1.0.0` tag is allowed to publish only after the tag workflow passes all of the following:

- tag / VERSION identity verification;
- version metadata and release-contract verification;
- Core Release-mode test suite;
- Windows desktop/runtime smoke suite;
- Windows 10 API compatibility build and smoke suite;
- x64 and ARM64 production builds;
- exact portable-package allowlist and embedded executable icon checks;
- packaged x64 startup smoke;
- SHA-256 generation and verification for both ZIPs;
- generated `update-manifest.json` validation;
- immutable release publication checks.

## Interactive sign-off carried forward from the beta.3 closeout

The final beta.3 development cycle received real-Windows validation for the high-impact regressions addressed during closeout, including Settings navigation repaint behavior, the minimal portable ZIP structure, managed Everything acquisition/lifecycle behavior, and Uninstall cleanup after managed Everything use. The project owner accepted the current product state for direct 1.0.0 promotion and chose to handle later non-blocking bugs through maintenance releases.

This promotion does not claim that future defects are impossible. It records that no currently known issue is being treated as a 1.0.0 release blocker.

## Post-release policy

- Confirmed regressions, compatibility issues, data-safety/security fixes and packaging defects may ship as 1.0.x.
- Existing user data and schema compatibility remain protected unless a future release explicitly documents and tests a migration.
- Search/ranking and numeric-intent behavior should not be changed in a maintenance release without a specific reproduced defect and regression coverage.

## 1.0.5 maintenance development validation

Asterun v1.0.5 is an unreleased maintenance candidate. Owner reported that clearing the Windows icon cache restored the new v1.0.4 icons after an in-place upgrade.

- Version: `1.0.5`; Windows fixed FileVersion/ProductVersion: `1.0.5.30000`.
- Settings / Commands / Usage / Provider Cache schemas remain 12 / 2 / 2 / 22 with no migration.
- The new Asterun.exe posts best-effort per-file Shell change notices only after successfully signaling the existing update-health event; the update worker from the previous version remains unchanged.
- No notifications are sent on ordinary startups or missing/unsignaled health events; the updater rollback, file replacement, signed archive/manifest checks and user data are untouched.
- The main Launcher's context-menu Shortcut Editor must return keyboard focus to its existing search EDIT on Save, Cancel and X, but only when that Launcher remains enabled, visible, and the active same-thread window. Preserve the search EDIT caret/selection as well as the query, and do not call Show() or steal global foreground. Hidden launchers, the Shortcut Manager and the established modal reactivation ordering are out of scope for behavior changes.
- Unpinned UserCommand results must not outrank stronger Provider relevance match kinds. `tea` should prefer TeamSpeak and TeamSpeak 3 Client over a fuzzy Notepad shortcut if one was manually added; deliberately created `np`/`ts` exact keywords and explicitly pinned overrides remain authoritative, with equal-kind user preference, bounded habits, prepared-index parity and stable transitive sorting.
- Two-character English queries can match the second word of an ordinary two-word, automatic primary application title (e.g. `ch` → Google Chrome), as a lower-priority BoundaryPrefix. This must not permit the same recall for UserCommand, system tools, restricted catalog or long multiword utility titles; continue to block arbitrary short substring/fuzzy noise. Regression covers `ch/chr`, `ed`, `fi`, `ph`, `te`, cached indexes, exact user aliases and existing `ad/so/to` limits.
- Normal catalog Provider short English filler words must never outrank genuine name prefixes via an accidental `Exact/Alias` promotion. Retain lower-priority token recall; don't demote user exact keywords/aliases, opaque short identifiers or restrictive-catalog intent. Regression checks model `7 Days to Die`, `Microsoft To Do`, `ToDesk`, `Tor Browser`, common `of/in` cases, usage learning and prepared indexes.
- New installs no longer seed the five historical UserCommands. The editable list starts empty, while normal Windows app Providers still discover Calculator and Notepad. Existing user-created shortcuts and optional imports remain intact.
- Microsoft Pinyin first-reveal regression: IME may be closed while `IME_CMODE_NATIVE` remains set. The final implementation requests alphanumeric conversion on EDIT focus and restores the original mode on hide/destroy while respecting explicit user changes. The obsolete delayed retry, opt-in diagnostic module, trace switch, logging, diagnostic-only test and documentation have been deleted. Permanent functional regression tests remain.
- Windows regression checks cover exact update notification targets, health-event gating, absent targets, preserved settings, Classic/Modern modal-close focus, direct typing, Up/Tab, Esc and IME mode handling. Build #1005 (Core, x64, ARM64, Windows 10 API baseline, desktop runtime smoke) passed. Owner accepted the scoped Windows 11 x64 icon, update-safety, search, input and fresh-install regressions on 2026-10-09. Physical ARM64 runtime acceptance is not claimed.
- This development branch does not alter `main`, immutable `v1.0.4` or existing Releases.
